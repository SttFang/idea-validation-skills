# 问题、场景与关键词（第 0–2 步）

想法不是搜索的单位。搜索需求的单位是「某人在某情境下卡住的那一刻」，一个想法通常对应五六个这样的时刻，每个时刻有自己的说法。两个人给同一样东西取同一个名字的概率不到 20%（Furnas 1987），所以只拿产品自己的词（例如「同步、记忆、技能」）去核量，核出零量只说明测错了对象，不说明没有需求。

第 0 步要回答的不是「这个产品有什么功能」，而是「谁在什么时候因为什么卡住、卡住有多痛、他们现在怎么凑合」。关键词、社区、竞品、付费、算钱都从这里推出来；这一步浅了，后面做得再细也是在错误的方向上用力。

依据标注：**有出处**＝文献或官方文档原值；**惯例**＝厂商或学界约定；**默认值**＝综合推断出的可调参数，在报告方法附录里声明。

## 第 0 步：先想透问题，再定场景

这一步决定后面所有调研的方向。旧版的毛病不是数据不够，而是对想法背后的问题想得太浅：把「同步、记忆、技能」当成需求本身，于是关键词、社区查询、竞品都围着产品词转。这一步要花的时间应该和取数相当，产出写进 `0-problem.md` 和 `0-scenarios.md`。

### 0.1 先访谈提出者

提出者就在对话里，是信息最全的人。用户给的一句话几乎总是把想法压缩过了，直接拿它去拆场景，就会把想法理解成产品词的组合（例如把「跨智能体迁移个人上下文」理解成「同步配置文件」）。动手前先问清楚下面几件事，一次最多问 4 个，用选择题加「其他」，答案写进 `0-problem.md` 开头：

| 要问清的 | 为什么 |
|---|---|
| 这个想法从哪来：你自己哪一次卡住了，当时在做什么，丢了什么、花了多少时间 | 提出者的亲身经历是第一个场景，也是最容易带偏的假设 |
| 核心资产是什么：用户真正在意、丢了会心疼的东西是哪些（举 2–3 个具体例子） | 决定场景和关键词围绕什么展开，例如「组会幻灯片、奖学金材料」和「配置文件」是完全不同的人群和说法 |
| 和现有产品比，差在哪里：你试过什么，为什么不满意 | 直接给出竞品清单和差异化假设 |
| 产品形态和谁付钱：个人订阅、按调用付费、企业采购 | 决定收入模型怎么算、去哪找付费证据 |
| 想法的全貌和这次验证的范围：有几块，先验哪块 | 避免把大想法缩成一个功能，也避免一次铺太开 |
| 第一批用户和市场 | 决定社区和关键词去哪些平台、哪些语言 |

规则：
- 只在提出者回答不了或说「你定」时才用自己的判断，并标为「代替提出者决定」。
- 用户在无人值守的环境里运行（不能提问）时，任务说明里必须带上述信息；缺了就在 `0-problem.md` 里逐条写出自己的假设，并在报告局限里说明「想法理解未经提出者确认」。
- 访谈得到的提出者经历，标为「提出者经历（待验证）」：后面要找到提出者以外的人也有同样经历，才算数。

### 0.2 去方案化

建一张**方案词表**：想法里所有功能名、技术名、产品名（例如「同步」「记忆」「技能」「云盘」「上下文」）。把原句改写成 3–6 条任务陈述，格式「动词 + 对象 + 情境限定语」，以动作动词开头（有出处：Ulwick）。任务陈述里方案词命中必须为 0。

> 错：同步记忆和技能。
> 对：换到另一台电脑后，继续推进同一个编程项目，不用重新交代背景。

### 0.3 问题树：从症状追到根因

以每条任务陈述受阻的**症状**为根，往下连问「为什么会这样」，直到原因不再能被继续追问，或已经落到人、组织、外部环境的层面。

- 同一个症状通常有多个原因，每个原因单独成枝。例：「新会话要重讲背景」可能因为工具不共享状态、说明文件分散在多处、换了智能体格式不通、团队成员各写各的。
- 每个根因写一句「如果它被解决，用户会得到什么进展」，以及「谁最受这个根因之苦」。
- 标出想法实际只解决了哪几枝；没覆盖的枝要么是新机会，要么是这个想法注定解决不了的部分，在报告里写明。

### 0.4 抽象阶梯与重构

- 往上问 3 次「为什么」，往下问 3 次「怎么做」（有出处：抽象阶梯）。往上每一级是一个更大的问题，常常对应更大的市场；往下每一级（手写说明文件、用 git 同步配置、接入记忆服务）是现有替代方案，**替代方案本身就是关键词种子**。
- 用四种重构手法追问（有出处：Wedell-Wedellsborg）：跳出框架（问题真的是 X，还是 Y）、重想目标（要的是同步，还是不被厂商锁定）、看亮点（哪些人已经没有这个痛，他们怎么做到的）、换位（团队负责人、智能体本身、公司安全负责人怎么看）。
- 写出这个想法属于哪个**更大的问题**，以及相邻的 2–3 个问题。用户往往是在解决更大的问题时顺带碰到这个问题，他们的说法也来自那个更大的问题。
- 产出：至少 2 个替代框架并写明取舍理由；至少 1 类「没有这个痛」的人，以及他们为什么没有。

### 0.5 场景发散：先列至少 8 个

按五个维度组合出候选场景，每个维度至少想 2 种取值：

| 维度 | 例子 |
|---|---|
| 谁 | 独立开发者、团队负责人、新入职成员、非开发的重度 AI 用户、智能体本身 |
| 什么时候 | 换设备、换智能体、隔几周重开项目、新人加入、出事故后复盘 |
| 用什么 | 哪几种工具组合、本地还是云端、有没有公司限制 |
| 多大规模 | 一个人、小团队、有合规要求的公司 |
| 代价多大 | 浪费几分钟、浪费额度和钱、出错上线、知识流失 |

先列出至少 8 个候选场景，每个一句话「当……时，……想……，但……」，再收敛。

### 0.6 场景快速取证

候选场景收敛前，先用免费或极便宜的数据各查一次「卡住的那一刻」有没有人说过：自动补全（问句开头）、Hacker News 和 GitHub 搜索（免费，见 `community-playbook.md`）。每个场景标一档：

- **有证据**：至少 2 名不同的人在公开场合描述过这个时刻；
- **证据弱**：只有 1 人，或只有自动补全里出现过相近说法；
- **无证据**：没找到。

收敛到 3–6 个场景时，优先保留有证据的；无证据但逻辑上重要的场景可以保留，但必须标「假设」，并在第 3 步专门去找证据。只靠提出者经历撑着的场景不能排第一。

### 0.7 重点场景写完整经过

对收敛后的每个场景写一段完整经过（有出处：Carroll 的场景叙事）：一次任务从开始到结束，用户在哪一步卡住、卡住时做了什么、花了多少时间或钱、最后怎么收场、多久会再发生一次。这段叙事是后面写关键词、写社区查询、判断付费意愿的依据，写不出来说明对场景还不够了解，回到 0.6 补证据。

### 0.8 场景卡片

每个场景一张卡，写进 `0-scenarios.md`：

| 字段 | 填写规则 |
|---|---|
| 标题 | 以「当……时」开头，不出现产品名或功能名 |
| 情境 | 至少三个具体限定：设备、时间、前一步在做什么、职业阶段 |
| 执行者与购买者 | 人还是智能体；两者是否同一人（企业市场常常分离） |
| 触发事件 | 可观察的事件，标注频率（每天、每周、每年） |
| 核心任务 | 动词 + 对象 + 情境限定语 |
| 任务地图 | 定义、定位输入、准备、确认、执行、监控、调整、收尾，这 8 步中属于哪几步 |
| 期望结果 | 2–5 条，「减少或增加 + 指标 + 对象 + 情境」 |
| 现在怎么凑合 | 至少 2 个具体做法，包括「什么都不做」 |
| 四种力量 | 推力、拉力、焦虑、惯性各一句 |
| 消费链任务 | 安装、迁移、学习、维护、退出时的麻烦 |
| 证据状态 | 有公开原话就附链接，没有就标「假设」 |
| 求助说法 | 这个人卡住时会怎么搜、怎么问（交给第 1 步，第 4 步用原话回填） |

### 0.9 完整性检查

- 每个核心任务的 8 步地图中至少 6 步写了期望结果，不适用的标「已检查，不适用」，不留空（默认值）。
- 相关任务、情感任务、社会任务、消费链任务各至少 1 条。
- 边界情况有记录：冲突、离线、敏感数据、跨厂商格式等。

### 0.10 细分判定

两两比较场景，下面六项里**任意两项不同**就算独立细分，分开研究、分开算钱（默认值，没有公开标准）：核心任务的动词或对象、执行者或购买者、触发事件及其频率量级、现有替代方案、首要结果指标、求助说法。最后一项要等第 1–4 步回填，所以场景切分在第 4 步之后要复查一次。

### 0.11 场景深度自检

逐条回答「是」才进入第 1 步：

- 访谈过提出者（或在无人值守时逐条写出了假设）吗？想法的全貌、核心资产、付费方、这次的范围都写清了吗？
- 写清了想法从哪来，并把它标成待验证的假设了吗？
- 任务陈述里没有任何方案词吗？
- 问题树里每个症状至少追到了两个原因、并且追到了根因吗？想法没覆盖的枝写出来了吗？
- 写出了更大的问题和相邻问题吗？
- 候选场景至少 8 个、覆盖了五个维度吗？
- 收敛后的每个场景都有证据档位，排第一的场景不只靠提出者经历吗？
- 每个重点场景都有一段完整经过，写出了卡点、代价和频率吗？
- 至少一类「没有这个痛」的人和至少 2 个替代框架写了吗？

「迁移与退出」「隐私与控制」这类横跨所有场景的约束，写成约束，不单独成为细分。

## 第 1 步：关键词设计

### 1.1 五类种子

每个场景 × 相邻 2–3 个认知阶段，生成五类种子词，写进 `keywords.csv`（`seed_class` 列）：

| 种子类型 | 认知阶段 | 例子（个人上下文类想法） |
|---|---|---|
| 问题 | 问题 | `claude forgets context new session`、`换电脑 配置丢了` |
| 变通 | 问题、方案 | `dotfiles claude code`、`git sync claude md`、`symlink agents md` |
| 替代对比 | 产品、决定 | `<竞品> alternative`、`<竞品> vs <竞品>`、`<竞品> pricing` |
| 品类 | 方案 | `ai memory layer`、`agent context manager` |
| 身份任务 | 问题、方案 | `share claude skills with team`、`freelancer switch between codex and cursor` |

认知阶段四档（`stage` 列）：问题（只描述症状）、方案（在找一类方法）、产品（在比较具体产品）、决定（价格、评价、购买）。这套对应关系是从业者共识，没有查询日志实证，所以每个场景要同时覆盖相邻的两三个阶段。

规则：
- 每个核心概念至少 5 个别名（有出处：词汇不匹配）。
- **原话种子不少于总数的三分之一**：社区里用户怎么描述卡住的那一刻，就怎么搜。第一轮社区数据还没有时先用模板生成，第 4 步拿到原话后回填。
- 每个词记 `source`（模板 / 社区原话 / 自动补全 / 相关搜索 / 竞品排名词）和 `upstream`（具体数据源），后面算丰富性要用。

### 1.2 扩展

自动补全（问句开头、字母前后缀）、相关搜索与「大家还在问」（结果页里有）、竞品网址拓词各扩一轮。相关词拓展接口对新品类常常只返回种子词本身，先买一批试，没有新词就不再买。用户改写查询时，重新措辞和接受系统建议合计约占 45%（有出处：Jansen 2009），所以自动补全是最接近真实改写路径的数据源。

## 第 2 步：关键词验证

### 2.1 核量与变体

中文市场没有谷歌搜索量可用，改用巨量算数热度、联想词和关联词，做法见 `community-playbook.md`「中文市场」；中英文分开核量、分开下结论。

- 一个国家一批拉月量；运行 `python3 scripts/keywords.py variants keywords.csv`。月量和 12 个月明细完全相同的词是谷歌合并的近似变体，组内只计一次，相加常虚高 2–3 倍（有出处）。月量不超过 20 或 12 个月都一样的小词不自动合并（它们常常只是一起落在最低分档），脚本会列出来，人工判断是否同义。
- **零量词不直接淘汰**：四条信号满足两条就保留，按最小量 10 计入排序（默认值）——自动补全能补出、结果页有论坛帖、社区有原话、所属簇的父主题有流量。报告原样写：「本报告的搜索量只覆盖已命名的说法；零量不等于没人需要，未命名需求见问题词与变通词簇。」

### 2.2 结果页意图判定

对每个候选词（多了就每个簇抽代表词）买一次结果页，运行 `python3 scripts/keywords.py serp data/serp-*.json` 得到前 10 条自然结果的网址、域名、标题和页面模块。逐条判两件事：这条结果是否属于目标场景；页面类型（教程、论坛、工具或产品页、榜单、文档、无关）。

- 前 7–10 条里至少 5 条属于场景＝`匹配`；3–4 条＝`混合`，交人工复核；2 条及以下＝`不匹配`，剔除（默认值）。不匹配时先加限定词重跑一次。
- 页面类型给出阶段信号：教程和论坛为主＝问题阶段；榜单为主＝比较阶段；工具和产品页为主＝方案或决定阶段。出现「讨论与论坛」模块的词几乎都是信息意图（有出处：Ahrefs，98.7%），但 AI 概览的意图分布在变化，只作参考。
- 一个词可以有多种意图（约 25% 的查询意图模糊，有出处），就写成「主要意图 + 次要意图」。

### 2.3 撞词检测

满足任一条就标 `collision=是`，剔除并把撞词方向的词加进否定词表（默认值，没有公开方法）：

- 前十中属于目标场景的结果不超过 2 条；
- 出现无关实体类型（例如 `claude md` 的结果是医生名录，MD 是医学博士）；
- 出现本地商家包或指向某个人的知识面板；
- 自动补全的下一个词大多指向别的领域。

### 2.4 聚类

运行 `python3 scripts/keywords.py cluster keywords.csv --serp serp-summary.json`：与簇代表词共享至少 3 个完整网址才同簇（惯例：Keyword Insights 默认 3；竞争激烈的领域取 4），意图标签不同的强制拆开。小众领域的结果页常常互不重合，一个都合并不了时，改用 `--level domain` 或降低 `--min-shared`，并人工看一遍。没买结果页的词按字面归到最相近的簇代表词（`cluster_basis=字面`）。后面所有计数按簇，不按关键词字符串。

### 2.5 对话渠道

AI 对话里的提问平均约 23 个词，远长于搜索的 3–4 个词（有出处：Semrush），完整的场景描述更多发生在这里。每个细分写 3–5 条约 20 词的场景提问（带身份、约束、目标），记在 `2-keywords.md`，作为下一步验证（问 AI 时会推荐谁）的输入。没做就在报告里写「未覆盖对话渠道」。

### 2.6 排序

意图契合是门槛不是乘数：`不匹配` 和撞词直接剔除；其余按 商业潜力（0–3）× 阶段权重 × log10(1 + 月量) 排序（默认值，需用真实转化数据校准）。每个场景、每个认知阶段至少保留 1 个簇，避免全部偏向高量的信息词。

### 2.7 准确性与丰富性

运行 `python3 scripts/keywords.py metrics keywords.csv --reference reference.csv`，结果照抄进 `2-keywords.md`：

| 指标 | 含义 |
|---|---|
| 意图精确率 | 判定过的词里，匹配记 1、混合记 0.5、不匹配记 0 的平均 |
| 撞词数 | 被剔除的撞词 |
| 冗余率 | 1 − 意图簇数 / 保留的词数 |
| 格子覆盖率 | 「场景 × 认知阶段」格子里有词的比例 |
| 种子类型分布、原话种子占比 | 五类是否齐全，原话种子是否不少于三分之一 |
| 召回率 | 参照说法中被找到的比例 |
| 估计说法总数与找到比例 | Chapman：N̂ = (n1+1)(n2+1)/(m+1) − 1 |
| 有效簇数 | Vendi 分数，必须和精确率一起看 |

**参照集**（`reference.csv`，列 `phrase, source, upstream`）在关键词定稿**之后**收集，来源要和关键词设计**独立**：例如第 4 步编码后社区原话里用户自己的说法、竞品排名词（Similarweb 带量关键词）。如果关键词和参照集用了同一个上游（比如都来自自动补全），重合会被抬高、估计偏低，脚本会提示，两者要合并为一个来源。

阈值暂不设硬门槛，只做相对比较；找到比例偏低时回到第 1 步补种子。意图契合分是诊断指标，用于剔除和比较，不作为优化目标：为了刷高契合分把词表收窄到只剩安全的品类词，会退回旧版的错误。

准确性如果用模型判定，要有人工复核：抽 50–100 个词由用户复评，一致度（κ）不低于 0.6 才采信；「不匹配」的判定全部人工复核，因为模型判「不相关」时只有约 68% 与人一致（有出处：Thomas 等 2024）。

## 回填闭环

第 4 步编码出的原话说法，要回填到 `keywords.csv`（`source=社区原话`）并重新核量；新出现的求助说法如果和现有场景对不上，回到第 0.5 步复查细分。关键词结果不仅回答「有多少人搜」，更重要的是回答「用户现在把这件事叫作什么、在用什么凑合」，这同时给出了细分边界和最早能转化的流量入口。
